面向小显存 GPU 的 RAG 重排推理跨层优化：详细实施计划

旧方案参考：当前选题已于 2026-11-16 切换为多模态文档视觉问答。本文件及对应的 72 单元矩阵属于原重排主题，不作为新主题的实施协议。

版本：v2.0 · 日期：2026-11-15 · 实施目录：/home/lxy18/system_homework/stage_2/

项目题目：面向完整查询完成时间的 RAG 重排推理优化——查询感知调度、CUDA Graph 执行与显存预算协同。

本计划收敛为三个优化项，分别位于服务调度、GPU 执行和显存管理层。三项共同解决一个问题：在 8GB 消费级 GPU 上，如何处理长短文档混合的重排请求，提高满足延迟要求的完整查询吞吐，同时保持排序质量和显存可控。

目前环境、模型和数据已经就绪，9 项环境验收通过；正式服务、三个优化模块和性能实验尚待实现。文中的参数是待校准的起点，收益门槛是工程目标，均不代表已取得的实验结果。

配套文件：实验协议草案、正式主实验矩阵、实施任务清单、本地数据核查。

1. 研究目标与课程要求

1.1 应用背景

本地知识库检索通常先检索出一组候选文档，再用交叉编码器对问题与候选逐对打分，最后返回最相关的文档。本项目实现这一重排服务：一条请求包含一个查询和 50 篇候选文档，输出完整分数和前 10 篇文档。

对交叉编码器而言，推理样本是 query-document pair；对服务用户而言，一次查询的全部候选完成后才得到结果。这两个粒度的目标可能不同：让短 pair 优先执行有利于填满高效批次，但也可能把同一查询的尾部候选推迟。与此同时，CUDA Graph 需要稳定形状，变长输入则要求在补齐计算、图命中和显存占用之间选择。

项目的研究价值建立在这一具体关系上：把推理执行的优化收益转化为完整查询的服务收益，并在受限显存上解释这条转化链路。

1.2 主目标

固定模型、精度、分词规则、候选集和延迟要求，以完整请求的 goodput 为主指标。一个请求只有在所有候选计算完成、结果有效且在 SLO 内返回时，才计入有效吞吐。

辅助指标包括查询 p50/p95/p99 延迟、SLO 达成率、拒绝率、pair/s、有效 token/s、padding 比例、图命中率、图缓存显存与峰值显存。排序质量使用 nDCG@10 和 MRR@10 验证。

3. 三个优化项及边界

编号 层次 改变的决策 独立开关 核心证据

O2 GPU 执行 同一批输入使用普通执行还是固定形状图重放 backend=eager/graph_hybrid 相同物理形状下的提交/执行时间及端到端变化
O3 显存管理 在预算内保留哪些图，以及如何复用通用工作缓冲 graph_set=fixed/budgeted，workspace=allocate/reuse 同预算性能、图覆盖、分配开销和显存曲线

O1 不改变模型与候选数量。O2 所需的固定图输入、输出地址是正确执行图的基础，不能重复计为 O3 的优化贡献。O3 的独立工作是预算化图集合选择，以及可在 eager 路径单独开关验证的通用缓冲复用。

三项形成协同：O3 提供可用图和代价表；O1 比较候选批次的查询收益与执行代价；O2 执行选择出的批次并反馈完成状态。项目贡献定位为这一系统机制与实测证据，而非声称长度排序或 CUDA Graph 本身是新技术。

4. 应用接口、数据结构与执行路径

4.1 服务接口

计划提供 POST /rerank：输入 request_id、query、包含 document_id/text 的候选列表及 top_n=10；输出每个候选的原始相关性 logit，以及按分数降序排列的前 10 个结果。分数相同时，以候选原始序号稳定排序。

主实验固定 K=50，敏感性实验使用 K=10 和 K=100。候选不足、重复 ID、无效类型等输入在推理前验证，空候选列表返回空结果并单独记录，不混入主性能统计。

API 层保持轻量。先以进程内 open-loop 回放完成机制验证，再补 HTTP 场景；两种边界分别报告，不混合为同一条曲线。

4.2 计划数据结构

结构 关键字段与职责
RequestState 请求 ID、到达/截止时刻、候选总数、剩余数、结果槽、状态
PairItem 请求 ID、文档 ID、候选序号、有效 token、长度；唯一标识实际推理工作
BatchPlan pair 列表、真实行数、物理 (B,L)、执行路径、预计代价、选择原因
GraphEntry 形状、图对象、固定输入输出、常驻显存、重放代价、可用状态

候选索引贯穿分词、排序、补齐、推理和结果恢复。一次请求允许被拆成多批，但只有全部真实候选完成后才进入 DONE。

4.3 执行路径

查询与候选原文
  → 接收、校验、有限队列
  → 公共分词与长度计算
  → O1：选择下一批候选
  → O3：提供可用图、形状代价与工作缓冲
  → O2：eager 或 CUDA Graph 执行
  → 按原始索引恢复分数
  → 查询聚合：全部候选完成后返回

首版只有一个 GPU 模型实例、一个 GPU 执行 worker，图之间串行执行。CPU 分词可以与 GPU worker 解耦，但各个对照共享线程配置。首版不做多图并发和共享图私有池，先把调度、显存和结果归属解释清楚。

5. 模型、数据与负载协议

5.1 固定模型行为

主模型使用已下载的 BGE base：12 层 XLM-R 编码器，hidden size 768，12 个 attention heads。统一 eval()、inference_mode()、FP16、SDPA、右侧 padding、最大 pair 总长度 512。截断采用统一的 longest_first，不为优化配置额外缩短 query 或 document。

所有变体固定 tokenizer 文件、special tokens、模型 revision、原始 logit 输出和稳定排序规则。候选长度在分词后确定；所有方法的真实 token 序列应一致。新增 padding、虚拟行与执行形状允许不同。

模型权重在启动时加载到 GPU，正式请求期间不重复传输权重。FP16 与 SDPA 是共有基线条件，不纳入三个优化项的收益。

5.2 开发集与正式测试集

本地核查发现训练/测试 query ID 不重叠，但训练 ID 1291、871 的规范化文本在测试集中出现。规范化规则为 NFKC、casefold 和连续空白合并。先移除这两个开发查询，官方 300 个测试查询全部保留。

对剩余 807 个开发查询，按 SHA256(UTF8("stage2-split-v2" + NUL + query_id)) 排序：前 128 个为 calibration，随后 64 个为 validation，剩余 615 个保留作后续诊断。正式测试前保存实际 ID 列表和哈希。

calibration 用于形状代价、长度分布、候选图集合和初始参数搜索；validation 用于选择与冻结配置；test 用于最终质量与性能评估。开始正式测试后，不根据测试结果重新挑参数再把同一批测试称为首次评估。

5.3 固定检索候选

使用已安装的 rank-bm25==0.2.2，固定 BM25Okapi(k1=1.5,b=0.75,epsilon=0.25)。索引文本为 title + " " + text；采用 NFKC、casefold、正则 \w+ 分词，不做随机采样或相关性标注干预。

按 BM25 分数降序、文档 ID 字符串升序打破同分，离线生成 top-100。K=10/50/100 均取同一 top-100 文件的前缀。所有方法读取同一文件，BM25 不进入重排延迟。

保存 candidates.jsonl、split ID、tokenization 参考结果、原始资产哈希和候选文件哈希。离线 token 文件用于长度分析与正确性参考；在线端到端测试仍从原文执行分词，不以预计算 token 替代 CPU 工作后再声称端到端收益。

5.4 到达时间与重复回放

请求内容来自真实数据；到达时间是可复现的合成负载，标明为回放。主实验使用 Poisson 到达，固定种子 1701、1702、1703；补充实验使用固定间隔与周期突发。

每个循环对 300 个测试查询做固定种子的随机排列，再进入下一循环。重复内容不启用结果缓存，也不跳过模型计算。重复回放增加服务事件数，不增加独立语义查询数。

各变体复用同一份 query 顺序与到达时刻文件。在线调度只看到已经到达、已经分词就绪的候选，不能访问未来请求。

6. 测量设计与校准流程

6.1 两个计时边界

端到端重排： 从计划到达时刻 t_scheduled 到完整结果可用 t_complete；同时记录实际接收 t_received，用于识别发送端落后。包含接收、分词、排队、组批、传输、推理及结果还原。

执行器诊断： 从已分词且已确定批次的输入开始，测打包、H2D、提交、forward、D2H 和结果恢复。用于归因，不替代端到端主指标。

CPU 时间使用单调高精度时钟，GPU 阶段使用 CUDA Events。记录实际 GPU 完成事件，不能把异步 replay() 或 forward() 的返回耗时当成推理完成耗时。各阶段可能重叠，时间线用于识别关键路径，分项耗时不能直接相加作为端到端耗时。

6.2 请求与批次日志

请求日志至少保存请求/查询 ID、K、计划/实际到达、分词开始结束、首次与末次批次完成、结果返回、SLO、状态、拒绝原因、候选完整性及结果文件路径。

批次日志至少保存 batch ID、pair ID 列表、真实行数、物理 B/L、有效 token 数、padding、执行路径、图 ID、预计/实际代价、可完成查询数、选择原因、阶段事件与显存统计。

GPU 输出分数在热路径只做必要归属处理；完整质量评估和图表计算离线完成。每轮保存配置、种子、软件指纹、模型/数据哈希、退出码与日志 schema 版本。

6.3 解释性指标

  • token padding 比例：1 - sum(real_lengths)/(B*L)，包含图尾批的虚拟行。
  • attention 工作量代理：1 - sum(real_lengths^2)/(B*L^2)，仅用于解释补齐，不等同于整个模型的耗时比例。
  • 图命中率：图执行批次数/所有批次数；另报告按真实 pair 数加权的命中率。
  • 查询跨批次数、最后一批等待、每批可完成查询数，以及按真实长度分组的等待分布。
  • 显存同时记录 PyTorch allocated、reserved、各图增量和设备可用量；不把三者当成同一口径。

6.4 有限校准空间

先调好共有基线，再测优化。batch 上限从 4/8/16/32 中选择，token 预算从 2048/4096/8192 中筛选可行值；总长不超过 512。起始图探测空间为 B={1,4,8,16,32}、L={64,128,256,384,512}，至多 25 个形状。

先逐个测 eager，再对可行形状做图捕获。形状的显存和捕获代价在独立进程或释放完整图对象后的清洁状态测量，不能把所有候选图同时留在 8GB GPU 上。每个形状预热至少 10 次，保存至少 50 次有效 GPU 计时，并检查是否跨越较大温度/频率变化。

O1 起始参数为窗口 8/16、完成奖励 0/0.5/1/2、组批等待 0/2ms。主服务队列上限先设为 32 条查询。参数搜索采用分阶段筛选，总计不超过 40 次短回放；在 validation 上选定一个正式配置，保存选择规则、所有试验与失败记录。

7. O1：查询完成感知的长度与代价组批

7.1 假设和实现对象

假设：在相同推理后端下，兼顾长度效率与整条查询的完成进度，可以改善“样本吞吐提高却查询完成变慢”的情况。

待实现 CompletionAwareScheduler，与 FIFO、长度/token 预算调度共享候选状态、队列上限和结果恢复代码。每次只选择下一批，不重排或删减返回的候选集合。

7.2 状态与候选动作

维护有限活动窗口、每个查询剩余 pair、到达时间、截止时间和就绪长度。活动查询按接收顺序进入窗口，完成后补入后续查询。

每轮产生两类候选批次：一类是相近长度的高填充批次；另一类优先包含某个查询的剩余候选，使该查询有机会在本批完成。批次真实行数受 B 上限、token 预算及已校准显存可行性约束。每轮候选动作总数限制为 64，避免调度计算成为新瓶颈。

不为了完成查询而无条件混合所有长度。一个 completion 批次只有在显存可行、代价可估计时才参与比较。

7.3 决策规则

先应用两个确定性保护：

  1. 查询年龄超过 0.5*SLO 时，优先推进最老查询；年龄阈值在开发阶段校准并冻结。
  2. 若某查询的预计 deadline slack 接近下一批执行代价，候选动作优先包含该查询。

其他情况使用如下效用排序：

progress(a) = sum(1 / K_of_pair) over real pairs in action a
complete(a) = number of queries fully completed by action a
utility(a) = (progress(a) + beta * complete(a)) / estimated_service_time(a)

beta 从开发集选择。代价来自已校准的 eager/graph 实际形状，包含相关提交与传输开销。平分时按 padding、最早到达序号、稳定 pair ID 排序，保证确定性。

slack 估计为截止时间减当前时间，再减该查询剩余候选的粗略执行代价；它是启发式估计，不构成 SLO 保证。首版冻结代价表，不引入学习模型或复杂在线训练。

7.4 停等与过载

存在就绪候选时，最迟在配置的组批等待上限触发执行；不为凑满图形状无限等待。达到队列上限的请求在接收阶段显式拒绝，拒绝计入主指标的失败分母。

已接收请求即使超过 SLO，也继续计算并记录迟到结果，避免中途取消引入额外状态。完整查询完成后释放状态。后续若增加取消功能，应另设协议和验证，本轮主线保持这一简单语义。

7.5 验证 O1

保持后端、图集合、候选集、线程和负载相同，比较 length_budget 与 completion_aware。同时测 goodput、查询 p95、pair/s、查询跨批次数和长文本等待。

关闭完成奖励、关闭年龄保护分别作机制消融。若 pair/s 与查询延迟的变化方向不同，保留两者，用批次完成数与等待时间解释。调度开销目标控制在服务 CPU 时间的 5% 内；超过时先减少候选动作和窗口，而非增加新优化主题。

8. O2：面向变长重排输入的 CUDA Graph 执行

8.1 假设和独立性

假设：对适合图重放的批次，在固定输入形状下减少 Python/CUDA 提交开销，可以提高有效执行效率；但补齐到图形状的额外工作可能抵消收益，因此需要 eager 回退。

实现统一 Executor.run(BatchPlan) 接口，提供 EagerExecutor 与 GraphExecutor。首次归因时固定同一个图集合和相同物理形状；O3 的集合优化随后单独打开。

8.2 图捕获与输入更新

对每个已选形状建立长期持有的输入与输出张量，完成同形状预热后捕获。固定模型处于 eval/inference 状态；捕获中不执行 .item()、CPU 同步或依赖当前输入值的 Python 分支。

每次重放前更新所有输入张量；真实 token 与 attention mask 原样复制，剩余列只补齐。尾批的虚拟行使用合法短句和有效 mask，输出按真实行数过滤，避免全零 mask 的特殊数值行为。

图输入输出地址与形状稳定是 PyTorch 的执行约束。PyTorch CUDA Graph 文档。

8.3 批次到执行路径的选择

对逻辑批次 n 条、最长 l，枚举能覆盖它的已捕获形状 B>=n,L>=l，同时保留实际长度 eager 动作。比较实测代价，而非默认选择最大的图或最长的图。

未命中、补齐代价高、显存准入失败或图不可用时，走 eager 并记录原因。正式测量期间不动态捕获新图；启动、捕获和冷缓存代价单独报告。

8.4 输出与缓冲生命周期

首版图串行运行，输出在下一次可能覆盖该地址的执行前，完成 D2H 或复制到独立结果槽。图完成事件前不得改写其输入。GPU 调用完成、CPU 拿到分数、整条查询完成是三个不同事件，分别记录。

CPU–GPU 传输保持各变体一致。以两组 int64 输入、B=16,L=512 为例，输入仅约 128 KiB；不能把模型权重大小作为每请求传输量来解释收益。本轮不单列传输流水线优化。

8.5 验证 O2

先用相同 batch 清单、相同 B/L、相同尾批补齐比较 eager 与 graph，区分图重放与形状变化的影响。再与动态 padding eager 比较总效果，解释额外 padding 和命中率。

保存 CPU 提交时间、GPU 时间线、forward 时间和 query goodput。标准 torch.compile 的 dynamic 与 reduce-overhead 配置作为官方优化对照；它不是第四项项目贡献。Sentence Transformers 推理优化文档。

9. O3：显存预算下的图集合选择与缓冲复用

9.1 假设和对照

假设：有限显存下，图的数量、覆盖形状与收益分布比“捕获越多越好”更关键。根据开发负载和实际图代价选择有限集合，可以改善同预算性能，或降低达到相近性能所需的显存。

使用两个可比较策略：fixed 是在开发集调优、满足预算的固定均匀形状集合；budgeted 根据真实长度/批次分布选择。不能故意把固定对照配置到 OOM，再把能启动作为性能胜出证据。

9.2 预算口径

在加载前记录设备可用显存，至少为宿主显示与外部波动保留 1 GiB；进程软预算上限初设为 min(6 GiB, free_at_start - 1 GiB)。预算包括模型、常规工作区、图常驻内存与通用缓冲，校准后写入协议。

图增量预算从 256/512/1024 MiB 做可行性筛选，正式主配置在 validation 阶段固定。显存敏感性以实际可行的三个预算点展开。CUDA 可用量与 PyTorch reserved 作为互补监控；外部显存竞争导致 OOM 的轮次保留日志并标记无效，不能悄悄降低输入规模。

9.3 图集合选择算法

对 calibration 得到的代表性逻辑批次集合 J，计算在图集合 G 下的代价：

cost(j, G) = min(eager_cost(j), compatible_graph_cost(j, s) for s in G)
C(G) = sum(weight(j) * cost(j, G))
gain(s | G) = C(G) - C(G union {s})
priority(s | G) = gain(s | G) / incremental_memory(s | G)

从空集或一个必要形状开始，反复加入正收益、能放入剩余预算且优先级最高的形状，至多保留 8 个图。每次加入后更新覆盖收益，避免重复计算同一批次的收益；显存增量由实际捕获测量或保守上界估计，并对最终集合实测复核。

该方法是可实现的贪心选择，不宣称全局最优。最终图集合、选择轨迹、估计收益、捕获顺序与实际显存全部保存，正式测试期间固定。

9.4 通用缓冲复用

复用普通打包、eager 输入和结果搬运的有限工作缓冲，采用明确的借出、执行、完成事件、归还状态。缓冲用完时等待或走受控分配路径，并记录次数，不无限扩容。

这部分以 workspace=allocate/reuse 在同一 eager 执行器上单独验证。O2 的图固定输入缓冲在两组都保留，不计入这项对照。若普通缓冲复用没有独立收益，只保留其作为实现细节，O3 的主要证据来自预算化图集合。

首版各图使用独立私有池，不做任意共享池复用。只有实际显存证据支持进一步研究时，再增加满足生命周期条件的共享池实现，并补充验证；本计划不依赖这项扩展。

9.5 验证 O3

在相同调度器、后端和显存上限下比较 fixed 与 budgeted，报告 goodput、峰值 allocated/reserved、图数量、覆盖率、eager 回退与启动成本。

画出“图预算—显存—goodput”曲线。O3 可以通过同预算更高 goodput，或相近 goodput 下更小显存形成证据；同时完整保留速度与内存结果。先固定评价口径，再观察结果，不能只挑更有利的一轴。

10. 协同执行与配置冻结

统一主循环如下，三个模块通过清晰的数据接口协作：

启动：加载模型 → 读取冻结的代价表 → 捕获 O3 选出的图 → 预热
重复：
  接收并分词已到达请求，更新就绪队列
  O1 枚举有限候选批次
  对每个候选，查询 O3 图目录和 O2 eager/graph 代价
  按年龄保护、slack 和查询完成效用选下一动作
  O2 执行动作，等待相应完成事件并保存真实分数
  更新剩余候选数，返回已经完整完成的请求
结束：drain → 校验账目 → 保存日志与环境指纹

配置冻结分三步：先固定公共基线与性能代价表，再固定 O1 参数，最后固定图预算和 O3 集合选择规则。使用 validation 验证组合后生成 protocol.lock.json，包含所有输入哈希和选择结果。之后的正式实验只更改实验矩阵中显式指定的算法与负载。

代号 调度器 执行器 图/显存策略 用途

B1 长度/token 预算 eager 统一通用缓冲 主强基线

主矩阵所有变体统一 workspace=reuse，使图集合和执行器对照不混入普通分配策略的差异。通用缓冲 allocate/reuse 放在独立诊断中，O3 主矩阵的证据由显存预算下的图集合选择提供。

另外做相同物理形状下的 eager/graph 微观对照。O3 依赖图集合，不能构造没有定义的“关闭 O2 但保留图集合收益”并称为完整 2³ 因子实验。

标准框架对照包括未修改的 CrossEncoder，以及官方推荐的 torch.compile 配置；TEI 作为可选生产框架对照，在固定镜像 digest 后运行。SDK 自带的长度排序予以保留，不能关闭现成功能制造弱基线。

SDK 的在线调用粒度固定为“一条查询的 K 个 pair”，使用开发集调优的 batch size，记录其内部分批与计时边界；离线 SDK 全局排序单独报告。编译对照分别检查 dynamic 与 reduce-overhead 的可行配置，保持同一有效 token 序列和 512 总长上限，不通过缩短输入换取加速。编译或外部框架若超出本机资源限制，记录配置与失败信息，保留可运行的标准 SDK 对照。

同服务壳消融对齐模型、分词、线程、候选、队列、SLO 和输出语义。整体框架比较可能涉及不同算子实现，作为实用性结果单独解释，不用于归因某一模块的因果收益。

12. 正式实验矩阵与统计协议

12.1 主实验

使用 SciFact 官方 300 个 test 查询，K=50，真实自然长度分布、FP16/SDPA、固定 SLO，主变体为 B1、S、G、SG、FULL、FULL-S。

先在开发集上测 B1 的饱和完成容量 mu_ref，再固定绝对到达率为其 50%、75%、90%、110%。所有变体使用相同到达率；110% 用于考察有限队列与过载行为。

每个变体、到达率使用 3 个种子，每次观测 120 秒，合计 6*4*3=72 个主实验单元，不含预热与 drain。预热至少 20 秒且完成至少 32 条开发集请求，排空预热队列后开始正式窗口。详细展开见 实验矩阵。每个单元在新进程中启动，按固定随机顺序交错变体；不在一轮中遗留前一个变体的图或显存状态。

12.2 SLO 的冻结

在开发集测调优基线的单查询 p95，主 SLO 初始定义为它的 2 倍，再保存为明确毫秒值。所有主变体使用这一值。K=10/100 若使用不同 SLO，必须在其对应开发集上提前定义，并分别报告。

SLO 既用于统计，也进入 O1 的截止时间估计。正式测量中不为某个算法单独改 SLO。

12.3 Goodput 与延迟记账

对观测窗口 [0,T) 中安排到达的 N 条请求，定义：

goodput = count(valid complete requests with latency <= SLO) / T
SLO attainment = count(valid complete requests with latency <= SLO) / N
latency = t_complete - t_scheduled

拒绝、失败、缺候选和超时均不能计入 goodput。窗口结束后允许 drain；只有属于该窗口到达集合的请求参与统计，不能混入预热或额外补发请求。请求即使在窗口外完成，只要端到端延迟符合 SLO，仍依上述固定分母记账。

drain 设明确上限 max(30 秒,10*SLO)；超出时保存未完成请求状态并计失败。完成请求的延迟分位数与拒绝/失败率并列给出，避免仅从留下来的请求推断所有请求的体验。

12.4 客户端与统计有效性

客户端按计划时刻提交，不等待上一请求完成后才发送下一请求。保存发送滞后 t_received-t_scheduled；若客户端不能维持目标速率，标记该轮的负载生成问题并定位，不把发送变慢解释成服务优化。

每次报告实际请求数与完成数。以每个独立运行为统计单位，再补时间块 bootstrap 表达相关性；保存区间计算代码和种子。p99 至少在配置累计 2000 条且覆盖 3 个种子时报告，否则以 p95 为主并注明样本量。少数语义查询的循环回放不能当成新的独立语义样本。

正式性能计时关闭 profiler。单独做短时间线；采样频率、日志级别和 CPU 配置各变体相同。温度、频率、功耗若接口可读则记录，不可读则注明，不能用零值代替。

12.5 辅助实验

  • K=10/100：B1、SG、FULL，在 75% 和 90% 对应基线容量下测 3 个种子；单独冻结候选数对应 SLO。
  • 低负载与突发：B1、FULL，分别验证等待与过载保护；突发模式先固定生成规则并保存 trace。
  • 长度诊断：按真实 pair 长度统计各桶效果；人为筛选的短/长子集作为诊断，不替代自然分布主结果。
  • 显存预算：SG 与 FULL，在三个可行预算点比较；固定 SLO 与队列规模。
  • 第二数据集或第二模型：主结果成立后优先选一个外部验证。备选为 NFCorpus 或 MiniLM，不要求全部扩展。

辅助矩阵先登记后执行，避免把所有因素全排列扩大工作量。正式主矩阵和正确性检查优先于外部框架数量。

13. 正确性与排序质量验收

13.1 输入与工作量一致

每个接收成功的请求必须计算相同 K 个候选；每个 pair 有唯一 ID。核查 pending、inflight、done 三个集合互斥，真实工作总数与接收请求的 K 之和一致。虚拟行不计入工作总数。

逐 pair 比较有效 token IDs、有效 attention mask、截断结果、候选 ID 和原始顺序。额外 padding 不能修改真实内容；不允许因超长或难处理而静默减少候选。

13.2 数值与排序

初始分数容差为 abs(error) <= 1e-2 + 1e-3*abs(reference)，在开发阶段检验后冻结。参考为相同模型与后端的 FP16 eager；对大误差或排名敏感样本再用 FP32 定位。

正式报告最大误差、分位数、近同分样本与 top-10 差异。nDCG@10 相对 FP16 参考的绝对下降不超过 0.001，MRR@10 变化一并报告；质量指标的 IDCG 使用完整 qrels，不只对命中的候选重新归一化。测试后不放宽容差掩盖实现问题。

13.3 边界与重放

覆盖尾批、虚拟行、跨长度桶、同一图连续输入变化、不同图交替、所有 buffer 槽回绕、单请求跨多批、重复文本不同 ID、无效请求、队列满与超时 drain。图输出必须属于当前请求，不能读取上次重放残留。

同形状 graph 与 eager、跨形状补齐、标准 SDK 结果分别比较。形式上输入相同不自动意味着 FP16 位级一致，因此结果归属和数值质量分开检查。

14. 可选 Z3 验证

主实验闭环后，用已安装的 Z3 对有限模型验证两类性质。

第一类是 pair 生命周期与索引映射：最多 4 条查询、每条 4 个 pair、batch 上限 4，建模 12 步内的入队、选择、执行完成与结果恢复，寻找重复、丢失、错误请求归属和重复写入的反例。

第二类是两槽缓冲生命周期：FREE → FILLING → INFLIGHT → READY → FREE，只有完成事件满足时才允许归还。检查 GPU 仍使用时不能再次覆盖，以及结果复制后才能复用输出。

保存界限、状态转移、断言、求解器版本、SAT 反例或 UNSAT 输出。有限展开证明的是对应界限与模型的安全性质；若增加归纳不变式验证，应单独写明归纳范围。该模型不证明 GPU 浮点等价，也不凭有限展开宣称无限期时限保证。

./run.sh report --run-dir results/<run-id>
./run.sh full --config configs/experiment.yaml
./run.sh reproduce-results --run-dir results/<run-id>

full 串起资产校验、候选构造、校准、协议冻结、正确性、正式测量和统计；已冻结协议可复用，不能每次 full 都悄悄重新挑正式参数。reproduce-results 从原始日志重算表格与图，不重新计时。

实验协议草案 是文档附录，标记 planning_only: true。实施后由 schema 校验并生成真正的运行配置，避免把尚未校准的值误当成机器最优参数。

16.3 每轮产物

results/<run-id>/ 保存 manifest.json、冻结协议副本、负载 trace、requests.jsonl、batches.jsonl、分数文件、stderr、退出码、质量报告、统计表和校验和。profiler trace 单独放入诊断目录并标明配置。

不覆盖旧轮次，不删除不利结果；无效轮次保留理由。源码、依赖锁、模型/数据来源和哈希可提交，巨型权重继续使用下载与验证脚本，打包时提供独立离线资产选项。

18. 阶段判断与工程目标

18.1 阶段门槛

  • 基线门槛：真实请求完成闭环，输入工作量与输出质量可验，长度/时间线能解释主要代价。
  • O1 门槛：相同执行器下观察查询完成行为与调度代价，长文本等待有记录。
  • O2 门槛：同形状图执行正确；自然负载的图命中、补齐和回退可以解释。
  • O3 门槛：同预算图集合与通用缓冲对照成立，测得实际显存而非只数图数量。
  • 提交门槛：至少两个不同层次有完整实测链路，三个计划模块均有实现、对照与结果记录。

18.2 预登记的性能目标

以 FULL 相对 B1 在固定 SLO 下 goodput 提高约 15%，或在相同负载、相近 goodput 下 p95 降低约 15%，作为阶段工程目标。O3 还需展示同预算下的性能或相近性能下的显存权衡。

这些数值用于决定是否继续调试与分析，不是已测结果、课程评分线或三项收益可相乘的承诺。每项的真实收益、开销及交互由消融呈现；报告结论限制在已验证的模型、硬件和负载条件内。

18.3 可能出现的现象与处理

现象 下一步分析与处理
分词占主要时间 先调好所有变体共有的预处理，再评估 GPU 主线；不临时增加新选题
查询长度多数接近 512 以真实分布检验调度与图开销，短文本子集用于诊断
graph 命中高但总时间增加 检查 padding、虚拟行、同步和总代价估计，保留 eager 回退
pair/s 上升而查询 p95 增大 检查每查询最后候选等待与完成奖励，验证 O1 的目标是否兑现
预算变化使固定图不可行 在同预算内重新选择合法固定对照，保留失败配置但不当作性能基线
Windows 后台/温度引入漂移 记录可用环境数据、交错重跑指定单元，原始轮次不覆盖
图缓冲复用导致结果串写 暂停性能计时，修复归属与事件依赖后重新验收
排序指标变化超阈值 检查 token/截断/分数语义与浮点误差，定位后冻结修正版本

19. 报告结构与交付验收

研究报告围绕同一主张组织：重排请求的用户目标是完整查询完成，调度与有限形状图执行需要在显存约束下联合决策。

建议结构为研究问题、系统与三项机制、实验方法、主结果、机制分析、相关工作和结论。避免把依赖安装过程或所有参数尝试作为正文主线，工程日志与完整数据放附录。

主图表建议包括：goodput 与到达率、query p95 与到达率、三项消融、相同形状 eager/graph 时间线、图预算—显存—goodput、质量一致性与误差分布。相关工作比较既有机制表，也有本机可执行的 SDK/框架结果；不用其他 GPU 上的论文数字替代同机对照。

最终提交应包含可审阅源码、报告、环境与配置清单、资产来源、原始/中间/结果数据、固定协议、运行步骤和一键或逐步复现入口。AI 辅助与 Z3 环境按实际使用情况记录。

项目完成的判断依据是：从真实输入到最终图表的证据链完整，三个优化项的作用边界可检查，其他人能按文档复现。

20. 相关工作与依据

  1. BGE reranker 模型卡：主模型、使用方式与任务定位；权重 revision 已由本地资产锁固定。
  2. Sentence Transformers CrossEncoder 源码：保留标准 SDK 自带的长度排序与结果恢复，实验以本地锁定的 6.3.0 实现为准。
